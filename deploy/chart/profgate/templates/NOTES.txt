3. Reach the API through the Service, which carries the API port only:

     kubectl -n {{ .Release.Namespace }} port-forward svc/{{ include "profgate.fullname" . }} 8080:{{ .Values.service.port }}
{{- if include "profgate.tlsEnabled" . }}
     curl --cacert ca.crt --resolve "<name>:8080:127.0.0.1" \
       "https://<name>:8080/v1/namespaces/<ns>/services/<svc>/targets"

   The API port serves HTTPS. <name> has to be a name the certificate is issued
   for, which is why the URL names it and --resolve sends it to the forwarded
   port: an address the certificate has no SAN for fails verification.
   ca.crt is the CA bundle that issued the certificate, exported from the
   issuer; a certificate chaining to an OS-trusted authority needs no
   --cacert.

   The certificate comes from the Secret {{ .Values.tls.existingSecret }} in namespace {{ .Release.Namespace }}, holding keys
   {{ .Values.tls.certKey }} and {{ .Values.tls.keyKey }}, mounted at {{ .Values.tls.mountPath }}. Create it before this release,
   or its Pods wait at mount time. A renewal written to the same Secret is
   picked up without a restart. The ops port stays plain HTTP, which is what
   the readiness probe and the metrics scraper use.
{{- else }}
     curl "localhost:8080/v1/namespaces/<ns>/services/<svc>/targets"

A Pod that runs but never becomes Ready is still waiting on a check the
gateway retries: the Kubernetes API preflight, the informer cache sync, or
the PGO-specific case, a NATS connection it cannot make. The Pod logs name
which of the three is still retrying. For NATS, check nats.url and the
path to it. A rollout stalls there rather than replacing a working
replica, which is the safe failure and does mean a NATS outage blocks
upgrades.
